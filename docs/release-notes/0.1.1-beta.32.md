# 0.1.1-beta.32 — tenant replay and persisted timestamp corrections

This release corrects tenant confirmation replay and persisted timestamp
fidelity, and improves tenant update-policy editing and updater recovery.

## Product changes

| Finding | Resulting behavior |
| --- | --- |
| Tenant update/delete confirmation replay | A successful exact retry is authenticated before mutable row/version checks and returns its recorded original outcome, including after deletion or a later edit. New receipts retain the resulting version; legacy ID-only receipts keep their scoped compatibility fallback. |
| Policy creation and file collection timestamp mismatch | The first result uses the persisted PostgreSQL value, so its serialized timestamps match subsequent reads and replay without rounding captured evidence. |
| Owned job folder duplication | A returned canonical folder round-trips through update without adding its tenant namespace again. Another tenant's canonical operator namespace remains rejected. |
| Hidden tenant update pins ([#341](https://github.com/BostonTechnologies/netratel/issues/341)) | The editor supports following the channel or setting/changing/clearing a version pin, shows effective policy, validates changed pin/channel combinations, and retains actor attribution and optimistic concurrency. |
| Updater local result identity conflict | Recovery requires a fresh authenticated Resume whose authoritative server revision and timestamp follow detection. It preserves the original outcome, conflicting bytes and recovery records before releasing the local fence. Archived unresolved delivery remains explicitly unresolved. |

Replay continues to enforce current identity, authorization, policy, resource,
instance, exact payload and original confirmation expiry. It adds no duplicate
write or accepted-operation audit. Fresh invalid/stale plans remain unconsumed.
The updater cannot treat an earlier Resume, late HTTP response or manual binary
replacement as acknowledgement of a conflicting installation outcome.

The existing result-delivery record and additive gateway policy timestamp carry
updater recovery authority; no new database migration is required. Existing
generic PR, main, release-build and publication workflows remain the gates.
Regression coverage extends the owning HTTP API, real PostgreSQL, component and
client-delivery test groups, including authority/expiry boundaries and recovery
races. Publication evidence reports their actual execution separately.
