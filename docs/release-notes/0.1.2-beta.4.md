# NetRatel 0.1.2-beta.4

Addresses [#431](https://github.com/BostonTechnologies/netratel/issues/431),
[#432](https://github.com/BostonTechnologies/netratel/issues/432),
[#433](https://github.com/BostonTechnologies/netratel/issues/433) and
[#434](https://github.com/BostonTechnologies/netratel/issues/434).

HTTP MCP creation now follows **Connection → Server access → Tenant access →
Policies → Review & create**. Each selected tenant gets one approved base policy;
server permissions get a separate Server access base. All access and narrower
choices expose supported operations, paths, execution/onboarding limits and exact
expiry. A responsive grouped review shows the connection, grants and policies
together. Credential and policies commit atomically, with a bounded encrypted
one-time-secret handoff for a lost response. Existing access editing reviews
and reconciles the corresponding base policies alongside grant changes.

Policy management shows active bases with nested client/operation exceptions.
Explicit deny wins; children remain inside their parent's identity, scope,
operation ceiling, lifecycle and expiry. Named tenants and searchable principal,
client and catalog operation choices replace identifier entry. Actions read
Edit, Disable, Revoke and Delete. Single and bulk deletion retain immutable
audit/tombstone history while removing effective access and ordinary inventory.
Explicit legacy consolidation preserves exact rule restrictions and reports
conflicts for separate review. Historical inactive records remain available
through the history filters; migrations do not rewrite existing grants.

Run the supplied migrations before starting the new API/Web. The product version
remains controlled solely by `Directory.Build.props`; use the matching verified
publication and digest-pinned Compose bundle described in
[release installation](../../release/INSTALL.md).

Focused source, component and PostgreSQL checks cover setup transactions,
secret recovery, policy hierarchy/lifecycle and legacy consolidation. Public
build/distribution integrity and owner deployment acceptance are separate states.
Owner retesting should reconnect with a new credential, read an approved tenant,
inspect an onboarding preview, exercise a scoped deny and cleanup, and check the
review screen in light/dark and narrow/wide layouts. Runtime connectivity,
capability and owner acceptance are not inferred from saving policies.

See [HTTP MCP setup](../mcp-http/setup.md) and
[policy management](../mcp-http/authentication.md#bounded-operator-policies-in-the-web-ui).
