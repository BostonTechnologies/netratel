# 0.1.1-beta.11 — Client operations and Netclaw investigations

This release fixes the services dialog regression, adds native service and
folder operations, expands CLI and both MCP transports, and introduces native
Netclaw investigations for operators and published monitoring Flows.

## Client services

The services dialog no longer closes when the client directory refreshes. Its
lifetime belongs to the dialog provider, independently of the launcher row.
Background refreshes retain the visible directory and stable client keys;
explicit close and navigation still dispose the viewer.

Windows and systemd clients can Start, Stop and Restart an exact inventoried
service. The native client uses Windows service control or a bounded systemctl
invocation without constructing a shell command. Controls require
`client.manage` and the negotiated `service-control-v1` capability. Unsupported
clients remain readable and do not advertise a control they cannot execute.
The NetRatel client service itself is protected from these controls.

Each operation has a stable UUID and a durable receipt. Reusing that UUID does
not send another command. The API validates the reported service and final
state; an accepted request alone is not reported as success. A lost connection
can leave an outcome unknown, which stays visible for investigation. Generic
script/task routes cannot submit or cancel a reserved service-control task.
Inventory and refresh remain protected by `telemetry.read`.

## Client folders

The file browser can create a folder and explicitly confirm deletion of an
empty folder. Nonempty folders, filesystem roots and protected paths are
rejected. Typed native directory deletion cannot turn into file deletion if
the remote path changes between inspection and execution. Unix names retain
significant leading or trailing spaces.

Entries display creation and modification timestamps when the filesystem
provides them. These come from the existing directory listing; there is no
recursive size or descendant-count scan. Folder controls follow current
`file.write` and `file.delete` permissions and negotiated client capabilities.

## CLI, HTTP MCP and stdio MCP

The same closed operation contracts now expose:

- Client hostname, friendly name and tags; confirmed metadata updates.
- Service inventory, refresh, Start/Stop/Restart and operation receipts.
- Folder creation/deletion through the existing files-v2 preview/confirmation
  flow, including timestamps in directory listings.
- Monitoring configuration, rules, static target groups, alert summaries,
  events, acknowledgements, clearing and silences.
- Flow templates, connectors, inert drafts, validation, dry runs, immutable
  publication and run history.
- Netclaw connection management, investigation creation and context selection,
  saved transcripts, sending, explicit approvals, reconciliation and archiving.

Application permissions remain distinct. Editing a draft requires `flow.edit`,
publishing requires `flow.publish`, and binding a published version to a rule
requires `flow.execute` in addition to monitoring management. Selecting all
tenant clients also requires `monitoring.targets.all`. File deletion requires
`file.delete`; moving a file requires both write and delete authority.

The API checks the canonical account, current credential grants, exact tenant
and applicable MCP policy. A relay service token does not become an operator.
AI context clients also undergo target-policy admission. Managed mutations
first return an authorized preview and require explicit confirmation; accepted
work remains separately subject to each operation's concurrency and retry
contract. Tool schemas and instructions describe revisions, stable request IDs,
pagination, terminal states and unknown delivery. See [CLI and MCP](../CLI_AND_MCP.md).

## Native Netclaw and AI Ops

Open **AI → Netclaw connection** (`/ai/integration`) in the intended tenant.
Generate a one-time pairing code on the daemon host with `netclaw daemon pair`,
enter the daemon address and code, and pair. The API exchanges the code and
verifies the authenticated native SignalR session before marking it connected.
Pairing enables the saved connection. Check its verification result before
starting investigations; a failed probe keeps the exchanged credential for
**Test connection** without consuming another pairing code.

The integration uses the same native protocol as RatelDesk: `/api/pair/exchange`,
`/hub/session`, `EnsureSession`, `SendMessage`, `ReceiveOutput` and
`RespondToInteraction`. Device credentials are protected at rest and never
returned in connection responses.

`/ai/ops` now contains a durable investigation workspace. Operators can open a
case with selected systems, inspect cases created from alerts, send messages,
read saved conversation history and answer actual pending approval choices.
Uncertain delivery is reconciled by reattaching to the existing remote session,
without automatically resending the operator's message. Replacing a daemon
endpoint does not silently attach an old transcript to a different daemon.

Flows can use **Investigate with AI** to start an alert-linked Netclaw
investigation. Draft validation and dry runs do not contact the daemon.
Published execution retains the existing current-authority and alert-intent
checks. The tenant selector on `/flows` is now beside the heading on the left.

Connection changes require `tenant.admin`. Investigation context/history needs
`telemetry.read`; creation and operation additionally use `client.manage`.
Sending and approval/reconciliation use `secret.use`; alert-linked data also
requires `monitoring.read`. The daemon's own NetRatel tool credentials remain
responsible for authorizing any subsequent system action.

See [Netclaw AI operations](../netclaw-ai-operations.md) for setup, Flow wiring,
the permission model, approval behavior and recovery procedures.

## Upgrade and acceptance

Upgrade the API, Web, migrations, HTTP MCP, CLI/stdio MCP and native clients
together. Apply the normal forward database migration; preserve the deployment's
Data Protection keys so protected integration credentials remain readable.
Older native clients can still be inspected, but the new control capabilities
become available after their upgrade and gateway reconnection.

Release packaging, public downloads, SBOMs, checksums, the digest-pinned Compose
bundle and all five public container images use the existing generic release
workflows. Their successful publication checks establish distribution integrity.
The owner's deployed Windows/Linux/Netclaw acceptance remains a separate test;
no live customer service action is claimed by this release note.
